## 1. Scope and method

- **Current state of every policy**, not only Stage 1: all row level
  security policies on `public` tables and on file storage
  (`storage.objects`), read from the system catalogue of a local database
  built from `supabase/migrations` (equal to Dev up to update 90; **Dev not
  inspected directly**).
- Appendix A is generated by `docs/tools/generate-from-database.py`
  (read-only SELECTs). For each policy: table, name, command, permissive or
  restrictive, roles, USING, WITH CHECK, functions referenced, automatic
  concerns, test files that mention the table.
- **Intended access** is taken from the policy's own name (policies are named
  in plain words, for example "people managers see clients"). Whether the
  condition actually matches the intention is **not verified** for every
  policy; that's the independent review's job.
- **A policy existing doesn't make a table secure.** Effective access also
  depends on SECURITY DEFINER functions (which bypass RLS), the service key
  in server code (ARC-001 §4), grants and the functions each policy calls.

## 4. Policies readable by every signed-in member (verified; need content review)

21 policies let any active member read the whole table: admin_designations,
app_modules, client_programs, client_teams, compliance_item_versions,
compliance_items, delegation_rules, delegation_shares, features, job_titles,
organisation, **record_events, records**, register_templates, registries,
registry_fields, registry_managers, request_types, team_leaders,
team_members, teams. Most are configuration. **`records` and
`record_events`** (records-type registers, such as asset lists) are readable
by every member: fine for asset lists, a concern if an organisation keeps
personal or sensitive information in a records register. **To review.**

Also: `live_signals` "signed-in people see signals" (`true` for
authenticated): change signals only, no content (assumption from the name;
to verify).
